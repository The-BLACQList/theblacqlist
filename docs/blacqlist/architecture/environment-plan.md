# Environment Configuration Plan: The BLACQList

**Product:** The BLACQList — National Black-Owned Business Discovery and Commerce Platform
**Last updated:** 2026-05-07
**Status:** Active — source of truth for all environment setup

---

## 1. Overview

The BLACQList operates across three environments. Each environment exists for a distinct purpose and is backed by a separate Supabase project. No production data ever flows to local or staging.

| Environment | Purpose | Supabase Project | Stripe Mode | URL |
|---|---|---|---|---|
| Local Development | Daily engineering work, schema changes, feature development | Local instance (Docker via Supabase CLI) | Test or none | `http://localhost:3000` |
| Staging / Preview | QA sign-off, product owner review, design review before merge | Dedicated staging project | Test mode (`sk_test_...`) | Vercel preview URLs |
| Production | Live product serving real users | Dedicated production project | Live mode (`sk_live_...`) | `https://theblacqlist.com` |

### Ground rules

- Production data never moves to staging or local. No exceptions.
- Staging uses test-mode Stripe keys. No real charges can be made.
- Local development does not require a cloud Supabase account — it runs the full Supabase stack locally via Docker.
- New environment variables must be set in all target environments before code requiring them is merged.

## 2. Local Development Environment

### Purpose

Rapid feature development without cloud dependency. Runs the complete Supabase stack (Postgres, Auth, Storage, Edge Functions) locally via Docker. Developers can build and test most product flows without touching staging or production infrastructure.

### Prerequisites

- Node.js 20+
- pnpm
- Docker Desktop (must be running before `supabase start`)
- Supabase CLI (`npm install -g supabase` or `brew install supabase/tap/supabase`)

### How local Supabase works

Running `supabase start` spins up a local Docker environment that includes:

- Local PostgreSQL database
- Local Supabase Auth service
- Local Supabase Storage (equivalent of all 3 production buckets)
- Local Supabase Studio at `http://localhost:54323`
- Local API at `http://localhost:54321`

The `supabase start` command outputs your local `SUPABASE_URL`, `ANON_KEY`, and `SERVICE_ROLE_KEY`. These values go into `.env.local` and are never committed.

### Local configuration file: `.env.local`

This file is not committed. Copy from `.env.example` and fill in values from the `supabase start` output.

```
# Generated by `supabase start` — values are localhost-only, safe for local use only
NEXT_PUBLIC_SUPABASE_URL=http://localhost:54321
NEXT_PUBLIC_SUPABASE_ANON_KEY=<local anon key from supabase start output>
SUPABASE_SERVICE_ROLE_KEY=<local service role key from supabase start output>

# Email — use Resend test mode key or leave unset to log to console
RESEND_API_KEY=re_test_xxxxxxxxxxxxxxxxxxxx
RESEND_FROM_EMAIL=dev@theblacqlist.com

# Sentry — leave unset in local; errors log to console only
# NEXT_PUBLIC_SENTRY_DSN=

# Stripe — only needed for payment flows; leave unset if not testing payments
# NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY=pk_test_...
# STRIPE_SECRET_KEY=sk_test_...
# STRIPE_WEBHOOK_SECRET=whsec_...
```

### Stripe in local development

Stripe keys are not required for most MVP development. Leave them unset unless the specific feature being developed involves a payment flow. When testing Stripe locally:

- Use Stripe test mode keys only (`pk_test_...`, `sk_test_...`)
- Use the [Stripe CLI](https://stripe.com/docs/stripe-cli) to forward webhooks to localhost: `stripe listen --forward-to localhost:3000/api/webhooks/stripe`
- The Stripe CLI outputs a local webhook signing secret — use this as `STRIPE_WEBHOOK_SECRET` in `.env.local`

### Email in local development

Two acceptable approaches:

1. Set `RESEND_API_KEY` to a Resend test mode key (`re_test_...`). Resend will accept the request but not deliver the email. Useful for testing the send logic.
2. Leave `RESEND_API_KEY` unset and add a guard in the email service layer that logs the email content to the console instead of sending. This is the recommended approach for development where Resend behavior is not under test.

### Sentry in local development

Do not set `NEXT_PUBLIC_SENTRY_DSN` locally. Errors should surface in the terminal and browser console, not be sent to Sentry. Setting the DSN locally creates noise in the staging/production error feed.

### Seed data

Run after applying migrations to populate the local database with development fixtures:

```
supabase db seed
```

Seed file location: `supabase/seed.sql`

Minimum seed data:
- 3–5 listings per entity type (restaurant, retail, service, entertainment)
- 2–3 test users with different roles: standard user, business owner, admin
- At least one verified and one unverified listing (to test both states)
- At least one pending claim (to test the claim review flow)

Seed data is development-only and must never be applied to the production database.

### Known limitations of local Supabase

- No Point-in-Time Recovery (PITR) — local is for schema and feature testing only, not data durability testing
- No production-equivalent performance — do not use local for load testing or query benchmarking
- Local Auth email confirmation links open in localhost — this works as expected for development
- Local storage buckets reset when `supabase stop` is called — uploaded files do not persist across local restarts unless using `supabase stop --backup`

## 3. Staging / Preview Environment

### Purpose

Quality assurance before production merge. Every pull request gets an isolated preview URL. Product owners and designers review features in staging before they are approved for production deployment.

### Vercel Preview Deploys

Every pull request to `main` automatically generates a Vercel preview deployment at a URL in the format:

```
https://theblacqlist-pr-[number].vercel.app
```

Preview deployments use the "Preview" environment variable set in Vercel. All PRs share the same staging Supabase project and database.

### Shared staging Supabase project

One Supabase project is dedicated to staging. All preview deployments point to the same staging database. This is acceptable for this project at current scale.

Implications:
- Test data created in one PR's preview may be visible in another PR's preview
- Do not use staging for performance benchmarking or load testing
- Reset staging DB data before major QA cycles if contamination is a concern
- Staging DB schema must be kept in sync with migrations as they are merged

### Staging environment variables (set in Vercel under "Preview")

| Variable | Value |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Staging Supabase project URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Staging anon key |
| `SUPABASE_SERVICE_ROLE_KEY` | Staging service role key |
| `NEXT_PUBLIC_SITE_URL` | `https://theblacqlist.vercel.app` (or primary staging domain) |
| `RESEND_API_KEY` | Resend test mode key or staging key |
| `RESEND_FROM_EMAIL` | Staging from address |
| `NEXT_PUBLIC_SENTRY_DSN` | Sentry DSN (tagged as `staging` environment) |
| `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` | `pk_test_...` — Stripe test mode |
| `STRIPE_SECRET_KEY` | `sk_test_...` — Stripe test mode |
| `STRIPE_WEBHOOK_SECRET` | Staging webhook signing secret |

### Email in staging

Use Resend in test mode or with a staging subdomain. Real emails should not be sent from staging during routine PR review. Deliberate QA testing of transactional email flows (confirmation, password reset) is acceptable using test recipient addresses. Do not send staging emails to real users.

### Sentry in staging

Configure a separate Sentry environment tag (`staging`) or a separate Sentry project. Staging errors must not pollute the production error feed. Sentry alert rules should be configured to suppress or downgrade staging notifications.

### What staging is for

- QA engineer sign-off on acceptance criteria
- Product owner review of new features before approval
- Designer review of UI implementation
- Regression testing before merge to `main`
- Exploring edge cases with test data

### What staging is not for

- Load testing or performance benchmarking
- Storing data that mirrors production (no real user data in staging)
- Long-lived test accounts — staging DB may be reset between QA cycles

## 4. Production Environment

### Purpose

Serving real users. Production is the only environment where real data lives, real payments are processed, and real emails are sent. Access to production configuration is restricted.

### Vercel production deployment

The `main` branch deploys to production automatically on merge. Production environment variables are set in Vercel under the "Production" environment — separate from Preview variables.

Production URL: `https://theblacqlist.com`

### Supabase production project

A dedicated Supabase project separate from staging. Configuration requirements:

- Point-in-Time Recovery (PITR) enabled — requires Supabase Pro plan or higher
- Automated backups retained for minimum 7 days
- Connection pooling via PgBouncer in transaction mode (required for Vercel serverless)
- All RLS policies enforced — no policy exceptions for production

### Stripe in production

Live mode keys (`sk_live_...`, `pk_live_...`) are set only after:

1. Stripe account is fully verified (business verification, bank account connected)
2. All webhook endpoints are registered in the Stripe Dashboard with production URLs
3. A test transaction has been run end-to-end in test mode on staging
4. Stripe rate limits and error handling have been validated

Live mode must never be set as a variable in local or staging environments.

### Email in production

- Resend production API key
- Authenticated sending domain with SPF, DKIM, and DMARC records configured and verified
- From address: `noreply@theblacqlist.com` (or per-category addresses as defined in email architecture)
- All transactional email templates branded with BLACQList identity

### Sentry in production

- Production DSN configured
- Alerts configured for error rate spikes, new error types, and performance regressions
- Source maps uploaded via `SENTRY_AUTH_TOKEN` in CI/CD pipeline (not stored in production environment)

### V2 additions (Anthropic, Algolia)

- `ANTHROPIC_API_KEY`: Set in production only when the AI-powered feature is ready to ship. Configure rate limits in the Anthropic Console before enabling.
- `ALGOLIA_ADMIN_API_KEY`: Set in production when the search indexing pipeline is ready. The client-safe search key (`NEXT_PUBLIC_ALGOLIA_SEARCH_KEY`) is set when Algolia search is surfaced to users.

### Production data rule

No test data. No seed data from development. Listings in production are real businesses submitted through the platform or manually curated by the BLACQList team. The production database is never seeded from `supabase/seed.sql`.

## 6. Secrets That Must Never Be Committed

The following variables have elevated risk if exposed. Each one represents a distinct attack surface.

| Secret | Risk if exposed |
|---|---|
| `SUPABASE_SERVICE_ROLE_KEY` | Bypasses all Row Level Security — equivalent to unrestricted database root access. An attacker can read, modify, or delete any data in the database. |
| `STRIPE_SECRET_KEY` | Allows arbitrary charge creation, refund processing, customer data access, and subscription manipulation. |
| `STRIPE_WEBHOOK_SECRET` | Allows an attacker to forge Stripe webhook events, triggering subscription activations, payment confirmations, or refunds without real Stripe events. |
| `RESEND_API_KEY` | Allows sending email as your verified domain. Enables phishing campaigns from `@theblacqlist.com`. |
| `ANTHROPIC_API_KEY` | Paid API with usage-based billing. Leaked key can result in large unexpected charges and service rate limiting. |
| `ALGOLIA_ADMIN_API_KEY` | Allows deleting or corrupting the search index, adding malicious data to search results, or exhausting the Algolia plan quota. |
| `SENTRY_AUTH_TOKEN` | Allows modifying Sentry projects, deleting issues, and accessing source maps which may expose proprietary code. |
| `AUTH_SECRET` | Allows forging session tokens — an attacker can authenticate as any user without credentials. |

### Enforcement

**`.gitignore` must include:**

```
.env
.env.local
.env.development
.env.staging
.env.production
.env.*.local
```

**`.env.example` (committed):** Documents all required variables with placeholder values and description comments. No real values. This is the only env-related file that is committed to the repository.

**GitHub secret scanning:** Enable GitHub's built-in secret scanning on the repository. This catches accidental commits of known API key formats (Stripe, Anthropic, Supabase, Sentry) before they are pushed.

**Vercel environment isolation:** Production variables are set only under the "Production" environment in Vercel — they are not inherited by Preview deployments. Staging variables are set under "Preview" only.

## 7. Supabase Project Setup Notes

Apply these configuration steps to both the staging and production Supabase projects. Notes specific to one environment are marked accordingly.

### Authentication settings

- Enable **Email provider** (email + password sign-in required for V1)
- Magic link: optional, enable if added to the auth flow
- Enable **email confirmation** — users must verify their email address before their account is fully active
- Configure Auth **redirect URLs**:
  - `http://localhost:3000` (allow for local development testing of Auth emails)
  - `https://*.vercel.app` (wildcard for all Vercel preview deployments — staging only)
  - `https://theblacqlist.com` (production URL — production project only)
- Set **JWT expiry**: 7 days (default — acceptable for this product)
- Configure **Auth email templates**: customize confirmation email, password reset email, and magic link email with BLACQList branding, color scheme, and support contact

### Row Level Security

- Enable RLS on all tables by default — this is enforced when tables are created via migration
- Never disable RLS on a table that holds user data or business listing data
- RLS policies are defined per migration — each table's policies live alongside its schema migration

### Extensions

Run the following in the Supabase SQL editor for both staging and production projects:

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
```

`pg_trgm` enables trigram-based fuzzy text search — required for the listing and business name search functionality.

### Connection pooling (production)

- Enable **PgBouncer** in **transaction mode** on the production project
- Vercel serverless functions open and close connections on every invocation; transaction mode pooling prevents connection exhaustion
- Use the **pooled connection string** in all server-side Supabase clients that run in Vercel functions
- The non-pooled direct connection string is used only for migrations (`supabase db push`)

### Point-in-Time Recovery (production only)

- Enable PITR on the production Supabase project
- Requires Supabase Pro plan or higher
- PITR provides recovery to any point within the retention window (typically 7 days)
- Confirm PITR is enabled before the first production data migration

### Automated backups

- Supabase Pro plan includes daily automated backups
- Retain backups for a minimum of 7 days
- Verify backup configuration is active before any production migration that alters existing data

## 8. Storage Bucket Configuration

Three storage buckets are required. Configure each in the Supabase Storage dashboard for both staging and production projects.

### `listing-media` — Public bucket

| Setting | Value |
|---|---|
| Visibility | Public |
| CDN | Enabled (Supabase CDN serves all files) |
| File size limit | 10MB (bucket-level maximum) |
| Allowed MIME types | Enforced in application layer: `image/jpeg`, `image/png`, `image/webp`, `image/gif` |
| Public URL format | `[SUPABASE_URL]/storage/v1/object/public/listing-media/[path]` |
| Path pattern | `[entity_type]/[listing_id]/[uuid].[ext]` |
| Example path | `restaurant/abc-123/cover-f7e2c1.webp` |

Notes:
- All files in this bucket are publicly accessible by URL — do not store private content here
- Per-type file size limits (logo: 2MB, cover photo: 5MB, gallery image: 5MB) are enforced in the application upload handler, not at the bucket level
- CDN caching means deleted or replaced files may be served from cache briefly — use unique filenames (UUID-based) to avoid stale cache issues

### `verification-docs` — Private bucket

| Setting | Value |
|---|---|
| Visibility | Private |
| Public URLs | Never generated |
| Signed URL expiry | 15 minutes |
| Allowed MIME types | `image/jpeg`, `image/png`, `application/pdf` (enforced in application layer) |
| Access pattern | Server-side admin review UI generates signed URLs on demand |
| Path pattern | `claims/[claim_id]/[uuid].[ext]` |
| Example path | `claims/claim-789/doc-a3f1b9.pdf` |

Notes:
- Only server-side admin functions may generate signed URLs for this bucket
- Signed URLs expire in 15 minutes — do not cache or persist them
- No RLS-based user access — access is controlled entirely at the application/service layer
- This bucket stores ownership verification documents submitted during the claim flow

### `receipts` — Private bucket

| Setting | Value |
|---|---|
| Visibility | Private |
| Public URLs | Never generated |
| Signed URL expiry | 15 minutes |
| Allowed MIME types | `image/jpeg`, `image/png`, `image/heic` (enforced in application layer) |
| Access pattern | Server-side owner receipt view generates signed URLs for the authenticated owner only |
| Path pattern | `receipts/[user_id]/[uuid].[ext]` |
| Example path | `receipts/user-456/receipt-2c8d3e.jpg` |

Notes:
- A user may only access signed URLs for their own receipts — enforced in the server-side route handler
- `image/heic` support is included because iOS devices default to HEIC format for camera photos
- Receipts are tied to verified purchase or service records — the upload handler verifies ownership before allowing upload

## 9. Local Development Quick Start

A new engineer should be able to go from zero to running local development in under 30 minutes. Follow these steps in order.

**Step 1: Install required tools**

- [Node.js 20+](https://nodejs.org) — check with `node --version`
- [pnpm](https://pnpm.io/installation) — install with `npm install -g pnpm`
- [Docker Desktop](https://www.docker.com/products/docker-desktop/) — must be running before Step 3
- [Supabase CLI](https://supabase.com/docs/guides/cli) — install with `brew install supabase/tap/supabase` (macOS) or via npm: `npm install -g supabase`

**Step 2: Clone the repository**

```
git clone [repository URL]
cd theblacqlist
```

**Step 3: Start local Supabase**

Ensure Docker Desktop is running, then:

```
supabase start
```

This command pulls and starts the local Supabase Docker stack. First run takes 2–3 minutes to download images. Subsequent starts are faster.

When complete, the output displays your local credentials:

```
API URL: http://localhost:54321
DB URL: postgresql://postgres:postgres@localhost:54322/postgres
Studio URL: http://localhost:54323
Anon key: eyJ...
Service role key: eyJ...
```

Copy these values — you will need them in Step 4.

**Step 4: Configure environment variables**

```
cp .env.example .env.local
```

Open `.env.local` and fill in the values from the `supabase start` output:

```
NEXT_PUBLIC_SUPABASE_URL=http://localhost:54321
NEXT_PUBLIC_SUPABASE_ANON_KEY=[anon key from output]
SUPABASE_SERVICE_ROLE_KEY=[service role key from output]
```

Leave Sentry, Stripe, and Anthropic variables commented out unless you are specifically testing those integrations.

**Step 5: Install dependencies**

```
pnpm install
```

**Step 6: Apply database migrations**

```
supabase db push
```

This applies all migration files from `supabase/migrations/` to your local database in order. Run this whenever new migration files are added by other engineers.

**Step 7: Seed the local database**

```
supabase db seed
```

Populates the local database with development fixtures (test users, sample listings, test claims). See `supabase/seed.sql` for what is seeded.

**Step 8: Start the Next.js development server**

```
pnpm dev
```

The application is now running at `http://localhost:3000`.

**Step 9: Access local Supabase Studio**

Open `http://localhost:54323` in your browser to access the local Supabase Studio — the same UI as the Supabase cloud dashboard, running locally. Use it to inspect tables, run SQL, review auth users, and browse storage.

## 10. Adding New Environment Variables

Every new environment variable must follow this process before the code requiring it is merged.

**Step 1: Add to `.env.example`**

Add the variable with a description comment and a placeholder value (never a real value):

```
# Resend API key for transactional email
# Get from: Resend Dashboard → API Keys
# Server-only — never prefix with NEXT_PUBLIC_
RESEND_API_KEY=
```

**Step 2: Add to this document**

Add the variable to the relevant group table in Section 5 with all fields completed: variable name, which environments require it, description, where to get the value, and whether it is server-only.

**Step 3: Set the value in Vercel**

Before merging any code that references the new variable:

- Set the variable in Vercel under the "Preview" environment (for staging usage)
- Set the variable in Vercel under the "Production" environment (if required in production)
- Confirm the value is set before the PR is approved — a missing variable in staging will cause the preview deploy to break

**Step 4: Announce to the team**

In the pull request description, note any new environment variables required. Engineers pulling the branch for local testing need to add the variable to their `.env.local`.

**Rule:** Never merge code that requires a new environment variable before that variable is set in all environments where the code will run. A deployment that crashes because of a missing variable is preventable.
